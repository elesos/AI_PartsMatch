2. 产品定位

本系统不是传统电商商城，而是一个面向工程机械行业的 配件智能选型与采购清单系统。

用户往往无法准确说出配件名称或配件编号，只能提供设备品牌、整机型号、铭牌照片、旧件照片、发动机型号、序列号或模糊描述。系统需要借助结构化数据库、RAG 知识库和 AI 大模型，帮助用户从不完整信息中推断并匹配正确配件。

一句话定位：

帮助叉车、挖机等工程机械用户，通过文字、图片、铭牌、Excel 和 AI 知识库，快速找到正确可适配的配件。

⸻

3. 背景与问题

工程机械配件采购存在以下痛点：

1. 用户不知道配件的准确名称。
2. 用户不知道 OEM 编号、Part Number 或 SKU。
3. 同一整机型号可能因年份、批次、序列号不同而使用不同配件。
4. 同一配件可能存在原厂件、副厂件、替代件、通用件等多种选择。
5. 叉车、挖机配件分类复杂，涉及发动机、液压、电气、底盘、传动、制动等系统。
6. 用户常通过照片、铭牌、旧件、包装标签来描述需求。
7. 海外用户可能使用英文、越南语或其他语言描述配件。
8. 人工客服需要反复确认信息，沟通成本高。
9. 配件手册、维修手册、爆炸图、历史查询经验分散，无法被系统有效复用。
10. 批量采购时，用户希望通过 Excel 一次性上传多个配件需求。

因此，需要建设一个“配件数据库 + AI 大模型 + RAG 知识库 + 人工兜底”的智能配件匹配系统。

4. 产品目标

4.1 用户目标

用户可以通过以下方式找到正确配件：

1. 输入 Part Number、OEM 编号、配件名称、设备型号进行查询。
2. 上传配件照片、铭牌照片、包装标签照片进行识别。
3. 输入叉车、挖机等设备的品牌、型号、序列号、发动机型号。
4. 上传 Excel 批量查询多个配件。
5. 在系统无法准确匹配时，提交人工查询。
6. 将确认后的配件加入采购清单。
7. 不需要支付和物流，也能先形成询价或采购意向清单。

4.2 平台目标

平台需要实现：

1. 建立结构化工程机械配件数据库。
2. 建立整机、发动机、序列号、配件之间的适配关系。
3. 建立 OEM 编号、替代编号、跨品牌编号的匹配关系。
4. 建立 RAG 知识库，管理配件手册、维修手册、爆炸图、历史人工匹配案例。
5. 借助 AI 大模型理解用户自然语言、图片识别结果和多语言描述。
6. 提高配件匹配准确率，降低人工客服介入比例。
7. 将人工确认结果沉淀回知识库和数据库。

7. 核心业务流程

7.1 单个配件查询流程

1. 用户进入配件查询首页。
2. 用户选择查询方式：
    * 输入配件编号；
    * 输入 OEM 编号；
    * 输入配件名称；
    * 输入设备品牌和型号；
    * 输入发动机型号；
    * 上传配件照片；
    * 上传整机铭牌；
    * 上传包装标签；
    * 输入自然语言描述。
3. 系统识别用户意图。
4. 系统进行多路匹配：
    * 精确编号匹配；
    * 替代编号匹配；
    * 设备适配关系匹配；
    * 发动机型号匹配；
    * OCR 铭牌匹配；
    * RAG 知识库检索；
    * AI 语义匹配。
5. 系统返回候选配件。
6. 用户查看配件图片、编号、适配设备、替代关系和匹配原因。
7. 用户确认配件和数量。
8. 用户加入采购清单。
9. 若无法确认，用户提交人工查询。

⸻

7.2 批量配件查询流程

1. 用户进入批量上传页面。
2. 用户下载 Excel 模板。
3. 用户填写多个配件需求。
4. 用户上传 Excel。
5. 系统解析 Excel 内容。
6. 系统逐行匹配配件。
7. 系统展示每一行的匹配状态：
    * 精确匹配；
    * 多个候选；
    * 信息不足；
    * 未找到；
    * 建议人工确认。
8. 用户确认或修改匹配结果。
9. 用户批量加入采购清单。
10. 未匹配项可一键提交人工查询。

⸻

7.3 图片识别流程

1. 用户上传图片。
2. 系统判断图片类型：
    * 配件实物图；
    * 整机铭牌图；
    * 发动机铭牌图；
    * 包装标签图；
    * 旧件编号图；
    * 爆炸图截图。
3. 系统进行 OCR 识别和图像识别。
4. 系统提取关键信息：
    * 品牌；
    * 设备型号；
    * 序列号；
    * 发动机型号；
    * Part Number；
    * OEM 编号；
    * 规格参数；
    * 外观特征。
5. 系统结合数据库和 RAG 进行匹配。
6. 系统返回候选配件。
7. 用户确认、补充信息或转人工。

⸻

7.4 未匹配转人工流程

1. 系统无法准确匹配时，提示用户“信息不足或暂未找到准确配件”。
2. 用户可以继续补充：
    * 更多图片；
    * 整机铭牌；
    * 发动机铭牌；
    * 设备品牌；
    * 设备型号；
    * 序列号；
    * 配件安装位置；
    * 旧件编号；
    * 所需数量。
3. 用户选择提交人工查询。
4. 系统生成工单。
5. 客服在后台处理。
6. 客服与用户沟通确认。
7. 客服确认配件后回填系统。
8. 系统将结果沉淀为历史匹配案例。
9. 用户可将确认结果加入采购清单。

10. AI 匹配与知识库设计

10.1 总体原则

系统采用：

结构化数据库 + RAG 知识库 + AI 大模型 + 人工回填

其中：

1. 结构化数据库负责准确数据。
2. RAG 知识库负责非结构化资料检索。
3. AI 大模型负责理解用户表达、综合判断和排序。
4. 人工客服负责低置信度和复杂场景兜底。

⸻

10.2 传统数据库负责什么

传统数据库管理确定性数据，包括：

1. SKU。
2. Part Number。
3. OEM 编号。
4. 配件名称。
5. 多语言名称。
6. 价格。
7. 库存状态。
8. 上下架状态。
9. 配件分类。
10. 设备型号。
11. 发动机型号。
12. 适配关系。
13. 替代件关系。
14. 用户采购清单。
15. 人工工单。

传统数据库用于回答：

1. 这个编号是否存在？
2. 这个配件多少钱？
3. 这个配件适配哪些机型？
4. 这个配件有没有替代件？
5. 这个配件是否上架？
6. 用户采购清单里有哪些配件？

⸻

10.3 RAG 知识库负责什么

RAG 知识库管理非结构化资料，包括：

1. 配件手册 PDF。
2. 维修手册。
3. 设备说明书。
4. 爆炸图。
5. 配件目录。
6. 历史人工匹配案例。
7. 常见问答。
8. 铭牌识别案例。
9. 替代件说明。
10. 多语言别名和常见叫法。
11. 客服经验文档。

RAG 知识库用于回答：

1. 某型号设备常见配件有哪些？
2. 某发动机型号对应哪些滤芯？
3. 某 OEM 编号是否存在替代件？
4. 用户描述的“这个液压泵”可能是哪一个？
5. 某配件在爆炸图中属于哪个位置？
6. 用户上传铭牌后，应如何推断设备版本？

⸻

10.4 AI 大模型负责什么

AI 大模型主要负责：

1. 理解用户自然语言。
2. 判断用户想找的配件类别。
3. 提取用户输入中的品牌、型号、编号、数量。
4. 将多语言描述转换为标准查询条件。
5. 解释图片 OCR 结果。
6. 综合数据库和 RAG 的结果进行排序。
7. 输出匹配置信度。
8. 输出匹配原因。
9. 判断是否需要人工介入。
10. 生成需要用户补充的问题。

⸻

10.5 匹配优先级

优先级	匹配方式	说明
P0	Part Number / OEM 编号精确匹配	最高优先级
P1	替代编号 / Cross Number 匹配	推荐兼容件或副厂件
P2	品牌 + 整机型号 + 序列号范围匹配	用于同型号不同批次
P3	发动机型号 + 配件分类匹配	适合发动机件和保养件
P4	铭牌 OCR + 数据库匹配	适合用户只上传铭牌
P5	RAG 手册/案例检索	用于复杂适配判断
P6	图片外观相似度匹配	作为辅助证据
P7	用户自然语言语义匹配	兜底候选
P8	人工确认	低置信度或高风险配件

⸻

10.6 置信度规则

置信度	状态	处理方式
≥ 90%	精确匹配	可推荐加入采购清单
70%-89%	高可能匹配	展示候选，提示用户确认
40%-69%	低置信度	建议人工确认
< 40%	未匹配	引导补充信息或转人工

关键限制

1. 发动机、液压、电气、制动等关键配件，低置信度不能直接标记为精确匹配。
2. 图片相似不能作为唯一依据。
3. AI 必须展示匹配依据。
4. RAG 检索结果必须可追溯来源。
5. 人工修正结果必须进入审核流程，不能直接污染知识库。

6. 配件详情页加载时间 ≤ 2 秒。

14.2 准确性要求

1. Part Number 精确查询准确率 ≥ 98%。
2. OEM 编号查询准确率 ≥ 95%。
3. 设备型号 + 配件名称查询准确率 ≥ 85%。
4. 图片识别首期推荐准确率 ≥ 70%。
5. AI 推荐必须输出置信度。
6. AI 推荐必须输出匹配依据。
7. 低置信度必须提示人工确认。

14.3 安全要求

2. 图片大小需限制。

5. 用户联系方式需脱敏展示。
6. AI 调用日志需保存。
7. RAG 文档需做权限管理。
8. 人工回填知识需审核后发布。

16. 验收标准

16.1 文本查询验收

1. 输入准确 Part Number 时，系统返回唯一配件。
2. 输入 OEM 编号时，系统返回原厂件和可替代件。
3. 输入整机型号时，系统展示该设备相关配件分类。
4. 输入发动机型号时，系统可推荐发动机相关配件。
5. 输入模糊描述时，系统返回合理候选或提示补充信息。

16.2 图片识别验收

1. 上传清晰铭牌照片后，系统能识别设备型号。
2. 上传发动机铭牌后，系统能识别发动机型号。
3. 上传配件编号照片后，系统能提取编号。
4. 上传模糊图片时，系统提示重新上传。
5. 无法识别时，系统引导人工查询。

16.3 Excel 上传验收

1. 用户可下载标准模板。
2. 用户上传模板后，系统可解析行数据。
3. 系统可逐行返回匹配结果。
4. 用户可批量加入采购清单。
5. 未匹配项可批量提交人工查询。

16.4 后台管理验收

1. 管理员可新增、编辑、下架配件。
2. 管理员可维护设备型号。
3. 管理员可维护适配关系。
4. 管理员可维护替代件关系。
5. 管理员可上传 RAG 知识资料。
6. 管理员可审核 AI 修正结果。
7. 客服可处理人工工单。

16.5 AI 匹配验收

1. AI 推荐结果包含置信度。
2. AI 推荐结果包含匹配原因。
3. AI 推荐结果可追溯数据来源。
4. 低置信度结果不能标记为精确匹配。
5. 人工修正结果可进入待审核知识库。

18. 关键风险与解决方案

风险	说明	解决方案
配件数据不完整	用户无法匹配正确配件	先录入高频品牌、高频型号、高频配件
同型号不同批次配件不同	容易推荐错误配件	增加序列号范围匹配
替代件关系复杂	原厂、副厂、兼容件容易混淆	建立替代件关系表并标注可靠度
图片识别准确率不足	用户上传图片质量不稳定	OCR + 人工兜底 + 上传规范提示
AI 推荐错误	错配会影响采购体验	展示置信度和匹配依据，低置信度转人工
RAG 文档过期	旧手册可能误导 AI	知识库支持版本管理和停用
多语言表达复杂	海外用户描述不统一	建立多语言别名库
人工工单过多	客服处理压力大	将人工结果回填知识库，逐步提升自动匹配率

20. 总结

本系统的核心不是完成在线交易，而是帮助用户准确找到叉车、挖机等工程机械设备所需配件。

系统建设优先级应为：

1. 先建设结构化配件数据库。
2. 再建设设备、发动机、序列号、替代件适配关系。
3. 然后接入 OCR、AI 大模型和 RAG 知识库。
4. 最后通过人工工单持续修正和沉淀经验。

核心原则：

数据库负责“准”，RAG 负责“懂”，AI 负责“问清楚、找线索、排候选”，人工负责“兜底和沉淀经验”。
